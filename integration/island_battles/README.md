# Island Battles lobby integration

Run `./scripts/test-lobby-acceptance.sh` from the repository root. The script runs the lobby's shared runner, `integration/run.py` of the lobby module that `go.mod` pins (from a temporary copy, since the module cache is read-only), which starts the lobby (its `cmd/lobby`) and the Island Battles backend as separate processes, the backend with `ISLAND_BATTLES_LOBBY_URL` and the lobby with the `LOBBY_GAMES` that `backend/cmd/lobby-games` prints, and this suite, which reaches both through the runner's one front URL, using the SDK's locked `integration` dependency group, which includes the generic lobby Python client. Shared lobby code stays unchanged.

These tests own game-specific assertions: generation one initializes on Island Battles lobby start; starting a started lobby again binds no second game; commands are authorized against the frozen roster and team ownership; roster players keep commands, state and the replay after their lobby is deleted; incremental batches and empty completed turns work; one player's completion waits for every roster player; final completion advances once and emits each player's next-generation event; rejected commands do not partially apply; a player who never plays makes their team lose at the turn deadline, which the waiting player's client applies; and other game keys create no Island Battles state. Generic lobby behavior is tested by the lobby's own suite, `integration/` in [`INTODAN/mpl`](https://github.com/INTODAN/mpl), which this script runs too.

The HTTP and event contract, including request UUID retries, error statuses, reservations, disconnected-player waiting and client recovery, is documented in the [Issue #6 task plan](../../docs/tasks/issue-6-player-generation-commands.md). The gameplay SDK is documented in [`clients/island-battles-python`](../../clients/island-battles-python/README.md); its bots are functions from `BotTurn` to `BotTurnResult` that `IslandBattlesClient` takes as `play=`, as shown in the example.
