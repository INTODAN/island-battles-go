# Shared game SDK scenarios

`scenarios.json` version 1 contains the executable scenarios used by both Python and TypeScript. `schema.json` validates the scenario format; `state.json` is the initial server fixture. Requirement IDs refer to [the behavior specification](../../docs/sdk/behavior.md). A new full game SDK must run every case. Generic lobby-only clients use their separate tests, because they do not implement gameplay.

The handwritten adapters live in [Python's test_conformance.py](../island-battles-python/tests/test_conformance.py) and [TypeScript's conformance.test.mjs](../island-battles-typescript/test/conformance.test.mjs). Neither adapter nor the shared scenarios are generated by OpenAPI. OpenAPI generates the SDK's HTTP boundary and wire models; the adapters exercise that generated code and the real handwritten runtime.

Each adapter reads the same scenarios and creates one test per scenario. It translates actions such as `send` into the language's public SDK call, injects fake HTTP/realtime responses, then compares outgoing requests, callbacks, and state with the shared expectations. A new scenario using existing actions runs in both languages without changing either adapter. A new action needs support in every adapter.

## Backend coverage

These shared scenarios run entirely in memory. Python uses `httpx.MockTransport` and fake Centrifugo handlers; TypeScript uses an injected fetch function and realtime factory. The real Go backend, PostgreSQL, and Centrifugo server are not started. The simulated server supplies controlled responses so retry loss, stale data, duplicates, and callback races are reproducible; it cannot verify actual persistence, authorization, or game simulation.

The backend participates separately through Huma schema exports and [live integration tests](../../integration/island_battles/README.md). In particular, [test_sdk_languages.py](../../integration/island_battles/test_sdk_languages.py) starts real Python and TypeScript clients in the same game and verifies that they complete a turn and receive the same next generation through the backend and Centrifugo. Run the local scenarios with the SDK test commands or `scripts/check-sdks.sh`; run the real stack with `scripts/test-lobby-acceptance.sh` from the repository root.

## Execution model

For each scenario, copy `state.json` and apply `initial` as top-level overrides. Each callback records its generation and holds at an explicit barrier until a `return`, `fail`, or `close` step. This lets scenarios control concurrent state changes without timing assumptions. Record all command HTTP attempts, including attempts whose response is lost.

| Action | Meaning |
| --- | --- |
| `start` | Start the SDK using the fixture lobby, a test credential, a scripted player factory, and fake HTTP/realtime transports. |
| `server` | Apply top-level `state` overrides; set GET/POST status overrides (zero means success) or the number of accepted command responses to lose. |
| `send` | Call the current receiver with `origin`, `destination`, and `amount`, without transforming their types. |
| `return` / `fail` | Release the current callback successfully or with a strategy exception. |
| `publish` | Deliver `game.next_generation` version 1 using current server state, with optional top-level state/type/version overrides. |
| `reconnect` | Deliver subscription recovery callbacks through the realtime transport, causing the runtime to reconcile. |
| `refresh` | Call the public refresh operation. |
| `wait_error` | Wait for the runtime's background failure and compare its semantic error category. A timeout is a failure. |
| `expired_send` | Attempt to reuse the captured receiver; require a closed/expired receiver error and no additional HTTP request. |
| `close` | Close the SDK, including an active callback. |
| `mark_gets` | Record the current HTTP read count for later assertions. |
| `assert` | Compare observed callbacks, generation, factory team colors, command requests, request identity relationships, startup ordering, unchanged read count, or closed resources. |

Steps with `error` must fail in the named category: authentication, protocol, closed, validation, transport/service, ordinary HTTP, or strategy failure. Map idiomatic language exceptions to these categories without accepting unrelated failures.

The fake server accepts identical UUID retries idempotently; reusing a UUID with changed payload is a test failure. A successful completion marks the current generation submitted when its ID matches. Responses contain the current server state. `transport_failures` simulates response loss **after acceptance**, including completion acceptance. It must be a transport exception, not an HTTP 500 status. An HTTP error override rejects a request before acceptance.

Assert semantic JSON equality with `request_id` removed for `requests`, exact equality for `same_requests`, and differing UUIDs for `different_request_ids`. Require valid version-4 request UUIDs independently. Each distinct command invocation must retain its identity across retries. Startup assertions require discovery HTTP before subscription acknowledgment and a reconciliation read afterward. Closing assertions include callback cancellation and transport cleanup.

Adapters inject yielding retry scheduling and drain runnable tasks between steps; success must not depend on elapsed wall-clock sleeps. Timeouts bound hangs rather than assert ordering. The complete behavior remains in the SDK, including actual schema parsing, retries, deduplication, and turn completion.

Add shared scenarios before modifying behavior. Keep inputs and expectations here instead of copying them into each adapter. Add a new action only when an existing action cannot express a meaningful case; update the format schema and every adapter together. Language-specific model/helper tests and real-backend integration complement these cases.
